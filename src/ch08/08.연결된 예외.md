# 08. 연결된 예외
> 하나의 예외가 다른 예외를 발생시킬 수 있다.

예외 A가 예외 B를 발생시켰다면, 예외 A는 예외 B의 `원인 예외(cause exception)`라 한다.

```java
try {
    startInstall();
    copyFiles();
} catch (SpaceException e) {
    InstallException ie = new InstallException("설치 중 예외 발생");
    ie.initCause(e);
    throw ie;
} catch (MemoryException me) {
    ...
```

위 코드는 `SpaceException`을 원인 예외로 하는 `InstallException`을 발생시키는 방법을 보여주는 코드이다.

이때 `initCause()` 메서드는 `Exception` 클래스의 조상인 `Throwable`클래스에 정의되어 있어<br>
`Exception`을 상속받는 모든 예외에서 사용가능하다.

- ⭐ `Throwable initCause(Throwable cause)` // 지정 예외를 원인 예외로 등록
- ⭐ `Throwable getCause()` // 원인 예외를 반환

---

왜 발생한 예외를 그냥 처리하지않고 원인 예외로 등록해서 다시 예외를 발생시킬까?

이유는 여러가지 예외를 `하나의 큰 분류의 예외`로 묶어서 다루기 위해서이다.

하나의 분류로 예외를 묶기 위해 `InstallException`을 `SpaceException`, `MemoryException`의<br>
조상으로 하여 `catch`블럭으로 작성하면 실제 발생한 예외가 어떤 것인지 알 수 없다는 문제가 생긴다.

또한 `SpaceException`과 `MemoryException`의 상속관계를 변경해야 한다는 것도 부담이 된다.

```java
try {
    startInstall();
    copyFiles();
} catch (InstallException e) {
    e.printStackTrace();    
}
```

---

따라서 예외가 원인 예외를 포함할 수 있게 한 것이다.<br>
이러한 방법을 사용하면 두 예외는 상속관계가 아니어도 상관이 없다.

```java
public class Throwable implements Serializable {
    ...
    private Throwable cause = this; // 객체 자신을 원인 예외로 등록
    ...
}
```

---

또 다른 이유는 `checked`예외를 `unchecked`예외로 바꿀 수 있도록 하기 위함이다.

`checked`예외는 본래 프로그래밍 경험이 적은 사람도 보다 견고한 프로그램을 작성할 수 있도록 유도하기 위한<br>
의미였지만 지금의 컴퓨터 환경은 많이 달라졌고 따라서 `checked`예외가 발생하여도 예외를 처리할 수 없는 상황이 발생하기 시작하였다.

그럼에도 컴파일을 위해 의미없는 `try-catch`문을 계속해서 추가해야했기에,<br>
`checked`예외를 `unchecked`예외로 바꾸어 예외처리가 선택적이게 되므로 예외처리를 하지 않을 수 있게 했다.

```java
static void startInstall() throws SpaceException, MemoryException {
    if (!enoughSpace()) throw new SpaceException("설치 공간 부족");
    if (!enoughMemory()) throw new MemoryException("메모리 부족");
}
```

위 코드를 아래와 같이 변경하여 보겠다.

```java
static void startInstall() throws SpaceException {
    if (!enoughSpace()) throw new SpaceException("설치 공간 부족");
    if (!enoughMemory()) throw new RuntimeException(new MemoryException("메모리 부족"));
}
```

본래 `MemoryException`은 `Exception`의 자손이므로 반드시 예외처리를 해야하는데 <br>
이 예외를 `RuntimeException`으로 감싸버렸기에 `unchecked`예외가 되었다.

따라서 더 이상 `startInstall()`의 선언부에 `MemoryException`을 선언하지 않아도 된다.<br>
// 메서드의 선언부에 작성된 예외들은 호출하는 곳에서 반드시 예외처리를 진행해야 한다는 의미이기에

- ⭐`RuntimeException(Throwable cause)` // 원인 예외를 등록하는 생성자
