# 19. 인터페이스 3
> 인터페이스를 사용하면 관계없는 클래스간 관계를 맺어 줄 수 있다.

- Unit
  - GroundUnit
    - Marine
    - SCV
    - Tank
  - AirUnit
    - Dropship

위와 같은 상속 구조를 가진 클래스 계층에서, `SCV` 클래스에는 기계화 유닛을 수리하기 위한<br>
`repair()` 메서드가 필요하다. `repair` 메서드를 정의하면 다음과 같다.

```java
void repair(Tank t) {
    // ...
}

void repair(SCV s) {
    // ...
}

void repair(Dropship d) {
    // ...
}
```

이런식으로 수리가 가능한 유닛의 개수만큼 오버로딩된 메서드를 정의해야하는 불편함이 있다.<br>
이를 피하기 위해 매개변수의 타입을 공통 조상 클래스로 하면 좋지만 공통 조상이 다르기에<br>
`GroundUnit g`, `AirUnit a`처럼 여러 메서드를 오버로딩해야하는 것은 똑같다.

```java
interface Repairable {}

class SCV extends GroundUnit implements Repairable {
    // ...
}

class Tank extends GroundUnit implements Repairable {
    // ...
}

class Dropship extends AirUnit implements Repairable {
    // ...
}
```

`SCV`, `Tank`, `Dropship` 3개의 각 클래스는 같은 인터페이스를 구현했다는 공통점이 생긴다.

실제 인터페이스 `Repairable`은 정의된 것은 하나도 없고, 단지 인스턴스의 타입 체크에만 사용될 뿐이다.<br>

이후 `repair`메서드의 매개변수 타입을 `Repairable`로 선언하면<br>
이 메서드의 매개변수로 `Repairable`인터페이스를 구현한 클래스의 인스턴스만 받아들여진다.

```java
...

class SCV extends GroundUnit implements Repairable {
    ...
    
    void repair(Repairable r) {
        if (r instanceof Unit u) {
            while(u.hitPoint != u.MAX_HP) {
                u.hitPoint++;
            }
        }
        System.out.println(u.toString() + "repair finished");
    }
}

...
```

`Barrack`, `Factory` 클래스에 건물을 이동시킬 수 있는 메서드를 추가하고자 한다.

단순히 두 클래스에 각 메서드를 추가하면 기능 구현이 가능하지만, 코드가 중복된다는 단점이 있다.

```java
interface Liftable {
    void liftOff();
    void move(int x, int y);
    void stop();
    void land();
}

class LiftableImpl implements Liftable {
    public void liftOff() { /* ... */ }
    public void move(int x, int y) { /* ... */ }
    public void stop() { /* ... */ }
    public void land() { /* ... */ }
}
```

인터페이스를 정의한 후, 이를 구현한 클래스를 작성한다.<br>
`Barrack`, `Factory` 클래스에 `LiftableImpl` 클래스를 포함시켜 내부 호출로 사용할 수 있다.

// `Liftable` 인터페이스를 `Barrack`, `Factory` 두 클래스에서 구현할 수 있지만<br>
// 그럴 경우 코드 중복이 여전히 일어나 인터페이스를 사용한 이유가 없다.

최종적으로 두 클래스의 이동 관련 메서드를 `LiftableImpl`클래스 한 곳에서 관리할 수 있게 된다.<br>
또한 작성된 `Liftable`인터페이스와 이를 구현한 클래스는 후에 다시 재사용될 수 있다.

# 인터페이스의 이해
> 인터페이스의 규칙이나 활용이 아닌, 본질적인 측면

- 클래스를 사용하는 쪽(`User`)과 클래스를 제공하는 쪽(`Provider`)이 있다.
- 메서드를 사용(`호출`)하는 쪽(`User`)에서는 사용하려는 메서드(`Provider`)의 선언부만 알면 된다.

위 두 가지 사항은 인터페이스를 이해함에 있어 반드시 염두에 두고 있어야 한다.

```java
class A {
    public void methodA(B b) {
        b.methodB();
    }
}

class B {
    public void methodB() {
        System.out.println("methodB()");
    }
}

class InterfaceEx {
    public static void main(String[] args) {
        A a = new A();
        a.methodA(new B());
    }
}
```

위의 경우 `A`클래스를 작성하려면 클래스`B`가 이미 작성되어 있어야 한다.<br>
그리고 클래스 `B`의 `methodB()` 선언부가 변경된다면, 이를 사용하는 클래스 `A` 또한 변경되어야 한다.

이처럼 직접적인 관계의 두 클래스는 한 쪽(`Provider`)이 변경되면 다른 한 쪽(`User`)도 변경되어야 하는 단점이 있다.

클래스 A가 클래스 B를 직접 호출하지 않고 인터페이스를 매개체로 해서 클래스 B의 메서드에 접근하도록 하면<br>
클래스 B에 변경사항이 생기거나 클래스 B와 같은 기능의 다른 클래스로 대체되어도 A는 전혀 영향을 받지 않도록 할 수 있다.

```java
interface I {
    public abstract void methodB();
}
```

```java
class B implements I {
    public void methodB() {
        System.out.println("methodB in B class");
    }
}
```

위와 같이 인터페이스를 구현하도록 한 후, 클래스 A를 아래처럼 변경한다.

```java
class A {
    public void methodA(I i) {
        i.methodB();
    }
}
```

클래스 A를 작성하는 데 있어 클래스 B가 사용되지 않았다는 점에 주목하여야 한다.<br>
클래스 A와 클래스 B는 직접 관계에서 I를 거치는 간접 관계로 바뀐 것이다.

클래스A는 인터페이스를 통해 실제로 사용하는 클래스의 이름을 몰라도 되며<br>
실제로 구현된 클래스가 존재하지 않아도 문제되지 않는다. 오직 직접적 관계에 있는 인터페이스 I의 영향만 받는다.

⭐ 인터페이스 I는 실제구현 내용(클래스 B)을 감싸는 껍데기이며,<br>
⭐ 클래스 A는 껍데기 안에 어떤 알맹이(클래스)가 들어있는지 몰라도 된다.

---

⭐ `JDK 8`부터 `디폴트 메서드`와 `static 메서드`, `JDK 9`부터 `private 메서드` 또한<br>
⭐ 인터페이스에 추가할 수 있게 되었으며 이들은 추상 메서드가 아니다.

`static` 메서드는 인스턴스와 관계 없는 독립적 메서드이기에 이전부터 인터페이스에 추가하지 못할 이유가 없었다.<br>
단지 학습적 이점상 규칙에 예외를 두지 않기 위해 `static` 메서드를 포함하지 않은 것이다.

인터페이스의 `static`메서드 역시 접근 제어자가 항상 `public`이며 생략 가능하다.

---

인터페이스에 메서드를 추가한다는 것은, 조상 클래스에 메서드를 추가하는 것처럼 단순한 일이 아니다.<br>
인터페이스를 구현하는 기존의 모든 클래스들에 새로 추가된 메서드의 구현을 작성해야 하기 때문이다.

`default`메서드는 추상 메서드의 기본적인 구현을 제공하는 메서드로<br>
추상 메서드가 아니기에 디폴트 메서드가 새로 추가되어도 해당 인터페이스를 구현한 클래스를 변경하지 않아도 된다.

디폴트 메서드는 키워드 `default`가 붙어야 하며, 추상 메서드와 다르게 일반 메서드처럼 `{}`이 있어야 한다.

```java
interface MyInterface {
    void method(); // public abstract
    default void newMethod(){} // public
}
```

디폴트 메서드 역시 접근 제어자가 `public`이며 생략 가능하다.

디폴트 메서드를 추가하면 기존 인터페이스를 구현한 클래스를 변경하지 않아도 된다.<br>
즉 조상 클래스에 새로운 메서드를 추가한 것과 동일한 것이다.

대신 새로 추가된 디폴트 메서드가 기존 메서드와 이름이 중복되어 충돌하는 경우가 발생할 수 있다.<br>
이러한 충돌을 해결하는 규칙은 다음과 같다.

- 1. 여러 인터페이스의 디폴트 메서드 간 충돌

> 인터페이스를 구현한 클래스에서 디폴트 메서드를 오버라이딩해야 한다.

- 2. 디폴트 메서드와 조상 클래스의 메서드 간 충돌

> 조상 클래스의 메서드가 상속되고, 디폴트 메서드는 무시된다.

---

`private`메서드는 클래스의 경우 자손들에게 영향을 미치지 않는다.<br>
인터페이스에서 역시 마찬가지이기에, `static`메서드 때와 마찬가지로 인터페이스에 추가되어도 문제가 없다.

`private`메서드는 단지 접근 제어자가 `private`인 일반 메서드이고 `default`메서드 또는 `static`메서드의<br>
중복 코드를 제거하거나 코드를 작업별로 분리하는 과정에서 자연스럽게 추가하게 된다.

`private`메서드를 작성할 때 지켜야하는 규칙은 다음과 같다.

- 1. 반드시 구현부(`{}`)가 있어야 한다.
- 2. 접근 제어자는 `private`이며, `static`도 붙일 수 있다.
